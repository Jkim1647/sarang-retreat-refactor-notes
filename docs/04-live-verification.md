# 03. 실제 화면 검증 — 로컬 DB에 붙여 돌려 보고 찾은 문제들

앞 단계 리팩토링은 DB 없이 검증했다(순수 함수 추출 + 특성화 테스트, `toSQL`, 엑셀 스냅샷, mock E2E).
이번 단계는 **로컬 PostgreSQL + API 서버 + admin + retreat-web 을 실제로 띄워** 화면을 하나씩 눌러 봤다.
mock 으로는 보이지 않던 문제가 12건 나왔고, 모두 고친 뒤 같은 경로로 다시 확인했다.

---

## 1. 검증 환경

| 구성 | 방법 |
|---|---|
| DB | PostgreSQL 16 (로컬), `npm run migrate:latest:dev` |
| 데이터 | `ALLOW_DEMO_SEED=true npm run seed:demo` — 가짜 이름/`010-0000-xxxx` 번호, 5개 부서 · 300명 · GBS 30 · 숙소 16 · 버스 4 |
| 서버 | `NODE_ENV=development`, `DATABASE_SSL=false`, **문자(ALIGO)·S3 설정 없음** — 실제 문자가 나가지 않게 |
| admin | `NEXT_PUBLIC_API_HOST=http://localhost:4000` (로컬 HTTPS 인증서 없이 붙이기 위해 env 로 덮어쓰기 추가) |
| 로그인 | Google OAuth 대신 로컬 `JWT_SECRET` 으로 `accessToken` 쿠키 발급. 계정 2개: 전체 역할 / 부서 행정 간사만 |

데모 seed 는 실수로 다른 DB 에 돌리지 않도록 두 번 막는다.
`ALLOW_DEMO_SEED=true` 가 없으면 멈추고, 데모가 아닌 수양회가 하나라도 있으면 멈춘다(실제로 테스트용으로 만든 두 번째 수양회를 보고 멈췄다).

### 자동화한 확인

- **admin 38개 화면 순회** (Playwright): 페이지마다 콘솔 에러 · 4xx/5xx 응답 · 화면 문구를 모은다. 전체 역할 계정 / 부서 계정 두 번.
- **화면별 호출 API → 서버 역할 대조**: 순회 중 호출된 API 를 모아 route 의 `checkRetreatAdminRoleMiddleware` 역할과 맞춰 seed 의 페이지 권한을 만들었다.
- **retreat-web live E2E** (`npm run e2e:live`, 4개): 수양회 신청 · 중복 신청 차단 · 셔틀 왕복 신청 · 리더 출석/일정변경/보고서 제출. 실행 후 DB 를 직접 조회해 저장 여부를 확인했다.
- **다운로드 13종**: 엑셀은 파일을 열어 시트/헤더/행 수를, 꼬리표 ZIP 은 이미지 수와 실제 이미지를 확인했다.

## 2. 찾아서 고친 문제

### ① 저장은 됐는데 응답은 실패 — 안내 문자 실패가 요청 전체를 실패시켰다 (server · admin)

**재현**: 문자 설정이 없는 서버에서 입금 확인 → `500`. 그런데 DB 는 이미 `PAID`.
운영에서도 문자 공급자가 느리거나 실패하면 같은 일이 생긴다.

- 관리자: 실패로 알고 다시 누름 → "입금 확인 대기 상태가 아닙니다".
- 참가자: 신청 커밋 후 문자 실패 → 실패 화면 → 재신청하면 "이미 신청한 내역".
- 리더 일정변경 승인: 문자가 **중간**에 있어서, 문자 뒤의 메모 저장 · 요청 상태 갱신까지 건너뛰었다.

**수정**
- `MessageFacade.notifyAfterCommit(context, send)` — 상태 변경 뒤 안내 문자 14곳을 감쌌다. 실패하면 로그를 남기고 `{ sent: false, error }` 를 돌려줄 뿐 throw 하지 않는다.
- 문자 자체가 목적인 요청(입금 요청, 리마인더 3곳)은 그대로 실패를 알린다(502).
- 입금 확인 두 곳은 응답에 `messageDelivery` 를 포함 → admin axios 인터셉터가 한 곳에서 "처리는 완료됐지만 문자가 발송되지 않았습니다" 경고를 띄운다.
- 문자 설정이 비어 있으면 `FormData` 가 `Cannot read properties of undefined (reading 'name')` 로 죽던 것을, 원인을 말하는 에러로 바꿨다.

**확인**: live E2E 신청이 문자 없이도 완료 화면으로 간다 · 입금 확인 시 성공 + 경고 토스트 · 서버 로그 `[SMS] 안내 문자 발송 실패 (handleRetreatRegistration)`.

### ② GBS 꼬리표 이미지에 일반 참가자가 하나도 없었다 (server, 기존 버그)

**재현**: 꼬리표 ZIP 이 22바이트(빈 ZIP). 같은 데이터의 엑셀 꼬리표는 297행.

**원인**: `.andWhere("urr.user_type", "!=", "STAFF")`. 일반 참가자는 `user_type` 이 `NULL` 인데,
SQL 에서 `NULL != 'STAFF'` 는 참이 아니다. 그래서 **새가족/군지체만 꼬리표에 남았다**.
같은 저장소의 엑셀 쿼리는 이미 `whereNull(...).orWhere(... != STAFF)` 로 맞게 되어 있었다.

**수정**: 이미지용 쿼리 3곳을 엑셀 쿼리와 같은 조건으로. **확인**: GBS 31장 · 부서 205장, 실패 0 (2.5s / 9.7s).

### ③ 엑셀 시간·요일이 서버 TZ 에 따라 달라졌다 (server)

**재현**: 14:00 출발 버스가 시트 이름에 `(23:00)`, 식수 엑셀 헤더가 `목저|목아|…` (수요일 저녁이 목요일로 밀림).

**원인**: `toKST()` 로 9시간을 더한 Date 를 `getHours()/getDay()/toDateString()` 로 읽었다.
로컬 getter 는 서버 TZ 를 한 번 더 적용한다. **운영 서버(UTC)에서는 맞고, KST 로 설정된 PC 에서는 틀린** 코드였다.
반대로 숙소 메모는 9시간을 더하지 않고 로컬 getter 를 써서 **UTC 서버에서 아침 식사가 전날 날짜**로 찍혔다.

**수정**: `kstParts(date)` — 9시간 더한 뒤 `getUTC*` 로만 읽는 헬퍼 하나로 통일.
**테스트**: `TZ=UTC / Asia/Seoul / America/Los_Angeles` 세 환경에서 같은 결과(이전 코드는 실패).

### ④ 상세 패널의 일정표에서 마지막 날 아침 열이 사라졌다 (admin)

**재현**: 신청 상세의 일정표가 `11/4 ~ 11/6` 까지만. 토요일(11/7) 아침이 없다.

**원인**: 날짜 열을 `toISOString().split("T")[0]` (UTC 날짜)로 만들었다. 아침 8시(KST)는 UTC 로 전날 23시라,
마지막 날 아침만 있는 날은 열 자체가 생기지 않았다. 참가자 웹(retreat-web)은 이미 KST 로 만들고 있었다.

**수정**: 공통 일정표 2개 + 일정변경 유틸을 `getKSTDateString` 으로. **테스트**: 토요일 아침 열/체크 회귀 테스트(이전 코드 실패 확인).

### ⑤ 입금 확인을 해도 위쪽 집계 표가 그대로였다 (admin)

**재현**: 입금 확인 → 테이블 행은 `입금 확인 완료` 로 바뀌는데 "입금현황 집계 표" 는 대기 5 / 완료 48 그대로. DB 는 4 / 49.

**원인**: 집계 표는 서버 컴포넌트가 처음 받은 데이터를 props 로만 받았고, 테이블은 SWR 캐시를 갱신했다.

**수정**: 집계 표를 테이블과 **같은 SWR 키를 fetcher 없이 구독**하는 클라이언트 컴포넌트로 감쌌다(추가 요청 없음). 재정 간사 화면도 같은 처리.
**확인**: 입금 확인 직후 3 / 50 으로 바로 바뀜.

### ⑥ 권한 없는 화면을 주소로 열면 "예상치 못한 오류" (admin)

**재현**: 부서 행정 간사 계정으로 `/retreat-payment-confirmation` 직접 접속 → HTTP 500, "Failed to fetch … 403 Forbidden".
클라이언트에서 불러오는 화면은 "Request failed with status code 403" 문구만.

**수정**
- 서버 컴포넌트용 fetch 17개가 각자 같은 코드를 복사하고 있었다 → `getFromApi()` 하나로 모으고 401 → `/login`, 403 → `/unauthorized`.
- 클라이언트는 SWR 전역 `onError` 에서 조회 403 이면 권한 없음 페이지로. 서버 판단이 기준이라 메뉴 데이터와 어긋나도 안전하다.

**확인**: 부서 계정으로 33개 화면 순회 — 허용된 3개만 열리고 나머지는 모두 `/unauthorized`.

### ⑦ 리더가 오늘 일정이 없으면 출석만 저장되고 보고서에서 실패 (retreat-web)

**재현**: 오늘 일정이 없는 리더가 제출 → 출석 9건 · 일정변경 1건 저장, 보고서는 서버가 거부 → "제출에 실패했습니다".

**원인**: 제출은 출석 → 일정변경 → 보고서 순서로 요청 3번. 서버 규칙("해당 날짜에 일정이 있는 리더만 보고서")을 클라이언트가 몰랐다.
(재시도는 안전함을 확인했다 — 같은 조원의 대기 중 요청은 서버가 upsert 한다.)

**수정**: 같은 규칙을 제출 전 검증에 추가 → 아무것도 저장하기 전에 이유를 보여준다. 단위 테스트 3개.

### ⑧ 기타

| 위치 | 문제 | 수정 |
|---|---|---|
| admin 테이블 20개 | 첫 렌더 중 `setState` 경고 (TanStack `autoResetPageIndex`) | 페이지네이션을 쓰지 않으므로 끔 |
| admin 식사·셔틀 체크, 셔틀 일정변경 2화면 | 같은 API 를 화면마다 `useEffect` 로 불러 local state 에 보관, 실패는 console 만 | `useShuttleBusInfo` SWR 훅, 쓰지 않는 state 5개·요청 1개(부서 정보) 삭제 |
| admin 권한 없음 페이지 | `href="javascript:history.back()"` (React 가 막을 예정) | `router.back()` 버튼 |

| 두 앱 토스트 · 다이얼로그 | 화면낭독기가 "Notification", "Close", "Toggle Sidebar" (영어) | "알림", "닫기", "사이드바 열기/닫기" |

## 3. 고치지 않고 확인만 한 것 (정상 동작)

- **GBS 라인업 실시간 반영**: 화면 2개를 열고 한쪽에서 GBS 변경 → 다른 화면이 새로고침 없이 `103 → 130` (소켓 `lineup-updated` 15건).
- **숙소 배정**: 5명 선택 → 형제 101호 배정 → 잔여 12 → 7, 미배정 140 → 135, DB 일치.
- **리더 일정변경 승인**: 금요일 저녁 제외 반영, 이력/메모 저장, 요청 `APPROVED`.
- **식사 체크**: QR 입력 → 확인 저장, 미신청 식사는 "추가" 후 확인까지.
- **참가자 웹 모바일(320px)**: 신청/셔틀/현황판/리더 로그인 가로 넘침 없음.

## 4. 남겨 둔 것 (판단이 필요한 것)

- **GBS 장소 배정 화면은 역할 2개가 필요하다.** 화면이 `line-up/gbslist`(LINEUP_STAFF)와 `dormitory/available-locations`(DORMITORY_STAFF)를 함께 부른다.
  인원관리 간사에게 라인업 역할이 없으면 화면을 쓸 수 없다. 운영 DB 의 역할 배정을 확인한 뒤 서버 역할을 맞출지 정해야 한다.
- 꼬리표 이미지는 1000px 고정 폭이라 오른쪽 여백이 크다(기존과 동일하게 유지). 카톡 공유용이면 내용 크기로 자르는 편이 낫다.
- 셔틀 일정변경 승인 흐름은 이번 seed 로 재현하지 못했다(신청 변경 요청 데이터가 없음).
