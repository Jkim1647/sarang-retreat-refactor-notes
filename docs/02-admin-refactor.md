# 01. Admin 리팩토링: 버그, 렌더 성능, 번들, 구조

> 대상: 관리자 웹 (Next.js 14, SWR, TanStack Table + react-virtual, Zustand)
> 브랜치: `refactor/portfolio`, 커밋 12개. 원본 기준 104개 파일 변경, +5,803 / −8,147줄

## 1. 버그 수정

### 1-1. 하나의 SWR 키에 서로 다른 모양의 값을 캐시

`/api/v1/retreat/:slug/info`를 세 화면이 같은 SWR 키로 쓰면서, 각자 fetcher에서 원하는 부분만 잘라 캐시했다.

| 화면 | 캐시에 넣은 값 |
|---|---|
| 숙소 배정 | 일정 **배열** |
| 탑승 스태프 배정 | 장소 **문자열** |
| 탑승 스태프 모바일 | `{ 장소, 부서·학년 }` **객체** |

이 때문에 숙소 배정 화면을 본 뒤 탑승 스태프 배정 화면으로 이동하면, 장소 자리에 배열이 들어가 React 렌더링 에러가 날 수 있었다(코드 분석으로 확인).

**수정**

- `useRetreatInfo`를 추가했다. 응답 원본(`retreatInfo`)만 캐시하고, 필요한 부분은 호출하는 쪽에서 꺼낸다.
- 같은 엔드포인트를 `useEffect` + `useState`로 따로 부르던 11곳도 이 훅으로 바꿨다. 이제 요청은 중복 제거되어 한 번만 나간다.
- 쓰이지 않던 `univ-group-info` 요청 하나도 제거했다.

### 1-2. 가상 테이블 셀이 갱신되지 않음

`VirtualizedTable`의 메모 비교 함수에 빈틈이 두 군데 있었다.

| 대상 | 비교하던 것 | 놓친 경우 |
|---|---|---|
| 행 | `row.original` | 컬럼 정의가 바뀌어도 다시 그리지 않음 |
| 셀 | `getValue()` | 값이 없는 표시용 컬럼, 다른 행을 클로저로 읽는 셀(예: GBS 정원 초과 빨간색)은 값이 그대로라 갱신 안 됨 |

**수정**

- 행: 컬럼 배열의 참조도 비교한다.
- 셀: `columnDef`와 `row.original`의 참조도 비교한다.

**검증**: jsdom + Testing Library(개발 의존성만 추가)로 테스트를 썼다.

- 기존 코드에서는 "3명" 상황인데 "2명"이 남는 것을 재현했다.
- 수정 후에는 갱신되고, 데이터가 그대로일 때는 메모가 유지된다(다시 그리지 않음).

### 1-3. 오래된 캐시로 덮어쓰기 (stale closure)

부서 신청, 입금 확인, 셔틀 신청 훅의 낙관적 업데이트 코드에 같은 패턴이 있었다.

```ts
// Before: 확인 창 → API 대기 → 그사이 폴링/소켓으로 캐시가 바뀌어도, 렌더 시점의 data 로 통째로 덮어씀
await mutate(data.map(item => (item.id === updated.id ? { ...item, ...updated } : item)));

// After: mutate 가 넘겨주는 최신 캐시를 기준으로 병합
await mutate(current => current?.map(item => (item.id === updated.id ? { ...item, ...updated } : item)));
```

모두 8곳을 고쳤다.

### 1-4. QR 체크(식사/셔틀) 화면

- **포커스 가로채기**: 100ms마다 무조건 QR 입력칸으로 포커스를 가져와서, 셀렉트나 모달 입력이 끊겼다. 이제 다른 입력칸·드롭다운·모달을 쓰는 중이면 가져오지 않는다.
- **통계 race**: 일정을 빨리 바꾸면 늦게 도착한 이전 일정의 통계가 현재 일정 통계를 덮어썼다. 이제 "현재 선택된 일정의 응답"일 때만 반영한다.
- **에러 경로의 오래된 값**: 에러 처리 코드가 클로저에 갇힌 이전 렌더의 `canAddMeal` 값을 읽었다.

## 2. 렌더 성능

### 2-1. GBS 라인업 표: 행 재사용과 O(n²) 제거

- **Before**
  - 소켓 이벤트가 하나 올 때마다 모든 행 객체를 새로 만들었다. 그래서 행 메모가 전혀 동작하지 않았다.
  - 셀 5종이 매번 `allRows.filter(...)`로 같은 GBS 인원 수를 셌다(행이 n개면 O(n²)).
  - 컬럼이 전체 데이터에 의존해서, 데이터가 바뀔 때마다 컬럼도 새로 만들어졌다.
- **After** (`utils/gbs-line-up/lineup-rows.ts`)
  - `buildLineupRows`: 그룹 인원 수와 리더 메모를 한 번의 순회로 계산해 행에 넣는다.
  - `reuseUnchangedRows`: 내용이 같은 행은 이전 객체를 그대로 쓴다. 한 사람이 바뀌면 그 사람과 인원 수가 바뀐 같은 GBS 사람들만 새 객체가 된다.
  - 셀은 자기 행만 읽고, 컬럼은 더 이상 데이터에 의존하지 않는다.
- **검증**: 기존 셀 계산을 테스트 안에 그대로 옮겨 두고, 무작위 300행에서 새 방식과 결과가 같은지 비교했다. 행 재사용 여부도 테스트한다.

### 2-2. 테이블 6개의 컬럼이 렌더마다 새로 생성

1-2를 고치면서 "컬럼 참조가 바뀌면 다시 그린다"가 됐다. 그래서 다음 단계로, 렌더마다 컬럼을 새로 만드는 테이블을 전수 점검했다(16개 중 6개).

| 원인 | 수정 |
|---|---|
| 훅이 `useCallback` 없는 함수를 반환 (입금 확인, 일정 변경, GBS 장소, 숙소 배정) | `useCallback` |
| `useDetailSidebar`가 렌더마다 새 객체를 반환 | `useMemo`, 컬럼은 `sidebar.open`만 의존 |
| JSX에서 `rows.filter(...)`를 바로 넘김 | 성별별 `useMemo` |
| 컬럼 훅이 데이터 훅을 한 번 더 호출 (SWR 구독이 2개) | 테이블이 가진 액션을 넘기고 ref로 읽음 |

부서 신청 표는 추가로 정리했다.

- `getRowId`를 지정해 정렬·필터·삭제 후에도 행 식별이 유지되게 했다.
- 모바일과 데스크톱 테이블 중 하나만 마운트한다(예전에는 둘 다 렌더하고 CSS로 숨김).

## 3. 번들: 엑셀/캡처 라이브러리를 필요할 때만 불러오기

`xlsx`, `xlsx-js-style`(수백 kB)과 `html2canvas`를 모듈 최상단에서 import하고 있었다. 그래서 내보내기나 업로드 버튼을 누르지 않아도 화면을 열 때마다 내려받았다.

- **엑셀 업로드 모달 4개**: `next/dynamic`으로 분리했다. 모달이 쓰는 xlsx와 템플릿 유틸이 같이 빠진다.
- **리더 보고서·숙소 템플릿 내보내기**: 클릭 핸들러 안에서 `await import(...)`로 불러온다.
- **화면 캡처(`html2canvas`)**: 캡처 핸들러 안에서 불러온다.

결과는 맨 위 표와 같다. 일부 화면은 dynamic import 런타임 때문에 +1 kB가 늘었다.

## 4. 구조 정리

- **`RetreatEditForm`**: 2,454줄 안에 14개 컴포넌트가 들어 있었다. 메인 폼(365줄)과 카드별 파일 6개(`edit/_components`)로 나눴다.
- **수정 폼과 생성 폼의 공통 부분**: `retreats/_lib/retreat-form`과 `retreats/_components/Field`로 옮겼다.
  - 일정·셔틀 상수, 날짜 입력 변환, `Field`
  - 포스터/QR 업로드: 두 업로드를 `Promise.all`로 동시에 보낸다.
- **`DormitoryAssignmentManager`**: 1,700줄을 페이지 껍데기(165줄)와 `assignment-manager/` 모듈 6개로 나눴다.
  - 테이블 4개, Shift 범위 선택 훅, 순수 함수 lib
  - lib에는 단위 테스트를 붙였다.
- **공통 유틸**
  - `getApiErrorMessage`: 같은 의미의 복사본 8개를 교체했다. 화면마다 원래 쓰던 기본 문구는 그대로 유지했다. `error.message`로 넘어가는 변형은 동작이 달라서 교체하지 않았다.
  - `saveBlob` / `fileNameFromContentDisposition`: 다운로드 코드 12곳과 파서 3벌을 대체했다. 테스트 포함.
  - `useDebounce`: 두 벌이던 것을 하나로 합쳤다.
- **확인 창**: `window.confirm` 4곳을 기존 `useConfirm` 다이얼로그로 바꿨다(CLAUDE.md 규칙).
- **미사용 코드 삭제**: 모듈 18개(2,864줄). 옛 테이블, 쓰이지 않는 웹소켓/폴링 훅, 중복 Provider 등이다.

## 의도적으로 하지 않은 것

- **이름만 같은 헬퍼**: `normalizeDormitoryLocation`, `buildScheduleMap`은 이름만 같고 동작이 다르다(`null` vs "미배정", 인자 형태가 다름). 억지로 합치지 않았다(저장소 규칙).
- **아직 가상화하지 않은 테이블**: 셔틀 입금 확인, 일정 변경 이력 등을 가상화하려면 실제 화면에서 스크롤과 레이아웃을 확인해야 한다. 브라우저 검증 없이는 진행하지 않았다.
- **`isMutating`이 컬럼 의존성에 포함됨**: 저장할 때마다 두 번 다시 그린다. 하지만 셀이 진행 중 상태를 보여줘야 하므로 정확성을 우선해 그대로 두었다.

## 면접에서 설명할 때

1. **버그 하나를 고치면 성능 문제가 드러나는 연쇄**: 셀 갱신 버그를 고치자 "컬럼이 렌더마다 새로 생기는 테이블"이 성능 문제로 드러났다. 전수 점검으로 원인 4종을 찾아 고쳤다. 정확성과 성능이 서로 맞물려 있다는 것을 보여주는 사례다.
2. **실제 서버 없이 검증하는 방법**: 로직을 순수 함수로 분리하고, 기존 계산을 테스트 안에 그대로 옮겨 두어 새 구현과 결과를 비교했다. jsdom으로 버그를 재현했다(기존 코드에서 실패 → 수정 후 통과).
3. **빌드 결과를 보고 다음 작업 찾기**: `next build` 출력에서 첫 로드 JS가 3~5배 큰 화면을 발견했다. 원인 라이브러리를 찾아 지연 로딩으로 바꿔 최대 69%를 줄였다.
